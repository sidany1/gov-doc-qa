**"基于 RAG 的政务文档智能问答系统"**
1. **解决什么问题**：政务文档多、靠人工检索慢、关键词搜索匹配不准确和全面；
2. **功能特性**：多文档批量导入、语义检索、文件名 + 页码溯源、资料没有就拒答（幻觉控制）；
3. **技术栈**：Python、ChromaDB、bge-small-zh（本地向量化）、DeepSeek、PyMuPDF；
4. **项目流程**：离线（解析→清洗→按页切块→向量化→入库）+ 在线（问题向量化→检索→拼 prompt→生成）；
5. **快速开始**：1. pip install -r requirements.txt ；2. 把 PDF 放入 pdfs 文件夹（或修改代码里 PDF_DIR 路径）； 3. 在项目根目录新建 .env，写入 DEEPSEEK_API_KEY=你的key；4. 运行 python main.py
6. **核心亮点**：非技术人员只需将pdf文件放入指定文件夹或直接替换文件夹地址，即可快速将文件导入向量库，形成政务知识库。并直接可用自然语言进行语义检索。本系统已对ai生成进行限制，将幻觉降到最低，保证知识回答的准确性。还对源文件进行了预处理的清洗和切块，提高数据纯净度，减少token的消耗。并且对回答提供精准的参考文件定位，用户可自行根据返回的参考文件名称和页码进行验证，让回答可追溯。
7. **难点**： 
   1. 我有遇到明明本该是同一行的内容。在从pdf里提取出来中间却隔了一个回车符，我发现，pdf文件对文字的排版其实是块与块在空间里的定位，而不是像word文件那样是同一段内容占据多行。因而我对pdf里提取的内容进行了段落清洗，将非没有结尾符号但有回车符号的段落里的回车符号去掉，将本段与下一段合并，保准语义的连贯性。
   2. 文末的文件名和页码。我本来应该将参考文件的文件名和页码交给大模型，让大模型提供给用户。但考虑到文件名和页码是为了提供可溯源性准备的，万一被大模型的幻觉污染了，反而会丧失可溯源性，于是我将文末的参考文献改成了系统自行拼接，这样最大限度的保证数据准确。
   3. 我对大模型进行了底层提示词的限制，保证在遇到数据库里没有的知识时不提供额外的回答
   4. 重复入库，每次运行脚本都会 `table.add`，而你的 id 是固定的 `ids_0、ids_1…`，第二次运行再 add 同样的 id，chroma 会直接报 "id 重复"；就算不报错，同一批文档也会存两遍、检索出重复结果。所以每次入库前先清空
   5. 块太小会把一个完整操作步骤拆散、检索拿不到完整上下文；块太大又会塞进无关内容、稀释相关性、浪费 token，块的大小是300，尽量保证覆盖某种东西的全部描述而又不会过长，浪费token。而需要留50 字重叠是让相邻块共享边界，防止信息正好在切分点被切断，导致大模型无法获得完整的参考文献
